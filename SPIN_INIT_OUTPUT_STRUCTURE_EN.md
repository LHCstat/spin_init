# `spin_init` Output Directory Reference

English | [Chinese](SPIN_INIT_OUTPUT_STRUCTURE.md)

This document describes every directory generated by `dpgen spin_init`, its
numbering rules, file provenance, and dependencies between stages.

The examples use:

```json
{
  "out_dir": "./run_spin",
  "scale": [1.0],
  "pert_numb": 1,
  "md_nstep": 3,
  "spin_incar": ["./INCAR.spin.1", "./INCAR.spin.2"],
  "pert_spin": [
    {"Rotation": {"angle": 45, "axis": [0, 0, 1]}},
    {"Canting": {"angle": [30, 60], "seed": 12345}},
    {"Scale": {"pert": 0.10, "pert_step": 0.10}}
  ]
}
```

## 1. Overall data flow

Structures and calculation results pass through five stages:

```text
Input POSCAR
    |
    v
00.scale_pert                   supercell, scaling, cell/atomic perturbation
    | POSCAR
    v
01.md                           one VASP AIMD task per structure
    | OUTCAR + XDATCAR
    v
02.disp                         every XDATCAR frame becomes one POSCAR
    | POSCAR snapshots
    v
03.spin                         magnetic configurations and VASP calculations
    | OUTCAR + OSZICAR
    v
04.data                         extxyz, raw, and NumPy data
```

The output root is exactly the `out_dir` value in PARAM; no suffix is added.
For example:

```json
"out_dir": "./run_spin"
```

creates:

```text
run_spin/
|- param.json
|- 00.scale_pert/
|- 01.md/
|- 02.disp/
|- 03.spin/
`- 04.data/
```

`param.json` is a copy of the input PARAM file for provenance. It is not a
complete record of runtime normalization: for example, when `md_nstep` differs
from INCAR `NSW`, validation follows `NSW` without rewriting the copy. A later
stage-only invocation may copy a newer PARAM into the same root.

`machine.json` is not copied automatically, so retain the exact submission
configuration separately. Arrows in the trees below show logical symlink
targets and omit the actual `../` sequences. OUTCAR, XDATCAR, OSZICAR, and logs
appear only after the corresponding calculations have run and been retrieved.

## 2. Numbering rules

### 2.1 Scale directories

Each scale value is formatted with three decimal places:

```text
scale-0.980
scale-1.000
scale-1.020
```

`"scale": [0.98, 1.0, 1.02]` therefore creates the same three branches in
every stage.

### 2.2 Structural perturbation indices

Structure indices contain six digits:

```text
000000    scaled structure without random box/atomic perturbation
000001    first perturbed structure
000002    second perturbed structure
...
```

`pert_numb=N` creates `N` randomly perturbed structures plus the `000000`
baseline, for `N+1` structures per scale.

### 2.3 AIMD frame indices

Stage 3 numbers XDATCAR frames from zero, using at least two digits:

```text
00    first XDATCAR frame
01    second XDATCAR frame
02    third XDATCAR frame
...
99
100
```

This is a snapshot index, not a structural perturbation index.

### 2.4 Magnetic configuration indices

Every snapshot and initial INCAR template contains one unchanged baseline:

```text
origin/000000
```

`origin` is a category parallel to groups such as `000-rotation`; the task
files live in its `000000` child. Other configurations are grouped by their
zero-based `pert_spin` input index and mode:

```text
000-rotation/R1     first variant of the first input item
001-canting/C2      second variant of the second input item
002-rota_cant/RC1   first variant of the third input item
003-random/Rand3    third variant of the fourth input item
004-scale/S4        fourth variant of the fifth input item
```

The three-digit group prefix is the input-item index, not the number of times a
mode has appeared. A later Rotation may therefore be `002-rotation`.

Different input items independently start from the template's initial moments.
Parameter lists inside one item retain their combinations, such as
`angle x axis` for Rotation and `R_angle x axis x C_angle` for Rota_Cant.
Rota_Cant applies Rotation before Canting within that item. Each local variant
directory is one VASP task; group directories are categories only.

## 3. `00.scale_pert`: structurally perturbed POSCARs

```text
00.scale_pert/
`- scale-1.000/
   |- 000000/
   |  `- POSCAR
   `- 000001/
      `- POSCAR
```

Path interpretation:

```text
00.scale_pert/scale-1.000/000001/POSCAR
|             |           |      `- independent structure file
|             |           `-------- first random perturbation
|             `-------------------- scale = 1.0
`---------------------------------- structure-generation stage
```

All POSCARs in this stage are regular files. `000000/POSCAR` is the supercell
after scaling; `000001...00000N/POSCAR` additionally contain random box and
atomic perturbations. Temporary files such as `POSCAR.supercell` and
`POSCAR1.vasp` are not retained in the final stage directory.

## 4. `01.md`: VASP AIMD tasks

Stage 2 creates one AIMD task for every Stage 1 structure:

```text
01.md/
|- INCAR
|- POTCAR
`- scale-1.000/
   |- 000000/
   |  |- POSCAR -> 00.scale_pert/scale-1.000/000000/POSCAR
   |  |- INCAR  -> 01.md/INCAR
   |  |- POTCAR -> 01.md/POTCAR
   |  |- OUTCAR
   |  |- XDATCAR
   |  |- fp.log
   |  `- [user_forward_files]
   `- 000001/
      |- POSCAR -> 00.scale_pert/scale-1.000/000001/POSCAR
      |- INCAR  -> 01.md/INCAR
      |- POTCAR -> 01.md/POTCAR
      |- OUTCAR
      |- XDATCAR
      |- fp.log
      `- [user_forward_files]
```

| File | Type | Source or purpose |
| --- | --- | --- |
| `01.md/INCAR` | Regular file | Copy of `md_incar`, shared by all AIMD tasks. |
| `01.md/POTCAR` | Regular file | Common POTCAR assembled in `potcars` order. |
| Task `POSCAR` | Relative symlink | Matching POSCAR under `00.scale_pert`. |
| Task `INCAR` | Relative symlink | `01.md/INCAR`. |
| Task `POTCAR` | Relative symlink | `01.md/POTCAR`. |
| `OUTCAR` | Retrieved output | Main VASP AIMD output. |
| `XDATCAR` | Retrieved output | VASP AIMD trajectory. |
| `fp.log` | Runtime log | Standard output/error log configured by DPDispatcher. |
| User forward files | Task inputs | Files such as KPOINTS or `vasp.slurm` from `fp.user_forward_files`. |

Stage-level POSCAR, INCAR, and POTCAR links are relative. Additional upstream
user-forward links may point directly to external source paths.

The fixed DPDispatcher lists are:

```text
forward_files:
  POSCAR
  INCAR
  POTCAR
  + fp.user_forward_files

backward_files:
  OUTCAR
  XDATCAR
  + fp.user_backward_files
```

VASP may create CONTCAR, OSZICAR, `vasprun.xml`, WAVECAR, and other files on the
compute node, but they are local only when explicitly included in
`fp.user_backward_files`.

A forwarded `vasp.slurm` simply exists in the task directory. A command such as
`srun vasp_std` runs VASP directly, while `sbatch vasp.slurm` submits the file.
Because ordinary sbatch returns after enqueueing, DPDispatcher may retrieve
outputs before the child job completes. Direct `srun` inside the Slurm job
managed by DPDispatcher is the recommended arrangement.

## 5. `02.disp`: independent AIMD snapshots

Stage 3 validates every AIMD task before publishing `02.disp`:

```text
02.disp/
`- scale-1.000/
   |- 000000/
   |  |- 00/POSCAR
   |  |- 01/POSCAR
   |  `- 02/POSCAR
   `- 000001/
      |- 00/POSCAR
      |- 01/POSCAR
      `- 02/POSCAR
```

Path interpretation:

```text
02.disp/scale-1.000/000001/02/POSCAR
|       |           |      |  `- independent valid VASP POSCAR
|       |           |      `---- third XDATCAR frame
|       |           `----------- AIMD of the first perturbed structure
|       `----------------------- scale = 1.0
`------------------------------- snapshot-collection stage
```

These POSCARs are regular files written from pymatgen `Xdatcar` structures.
They preserve the frame lattice, species and atom order, and coordinates.

Stage 3 performs two independent checks:

1. OUTCAR must show AIMD completion and the expected number of `TOTAL-FORCE`
   blocks according to `md_nstep`/`NSW`.
2. XDATCAR must exist, be nonempty and parseable, and return frames with
   consistent atom counts and species order.

Failure in any task prevents publication of a partial `02.disp`.

## 6. `03.spin`: magnetic tasks

### 6.1 Single `spin_incar`

String input adds no INCAR index layer:

```json
"spin_incar": "./INCAR.spin"
```

```text
03.spin/
|- POTCAR
|- tasks.json
`- scale-1.000/000000/00/
   |- origin/
   |  `- 000000/
   |     |- POSCAR
   |     |- POTCAR
   |     |- INCAR
   |     |- OUTCAR
   |     |- OSZICAR
   |     |- fp.log
   |     `- [user_forward_files]
   |- 000-rotation/
   |  `- R1/...
   |- 001-canting/
   |  |- C1/...
   |  `- C2/...
   `- 002-scale/
      |- S1/...
      `- S2/...
```

### 6.2 Multiple `spin_incar` templates

List input adds one `###-incar` directory per template:

```json
"spin_incar": [
  "./INCAR.spin.1",
  "./INCAR.spin.2"
]
```

```text
03.spin/
|- POTCAR
|- tasks.json
`- scale-1.000/000000/00/
   |- 000-incar/
   |  |- origin/000000/{POSCAR,POTCAR,INCAR,OUTCAR,OSZICAR}
   |  |- 000-rotation/R1/...
   |  |- 001-canting/
   |  |  |- C1/...
   |  |  `- C2/...
   |  `- 002-scale/
   |     |- S1/...
   |     `- S2/...
   `- 001-incar/
      |- origin/000000/...
      |- 000-rotation/R1/...
      |- 001-canting/{C1,C2}/...
      `- 002-scale/{S1,S2}/...
```

A one-item list still creates `000-incar`; only string input omits this layer.
Traversal order is:

```text
snapshot -> spin_incar input order -> pert_spin input order -> local variant
```

Each template supplies its initial `MAGMOM/M_CONSTR`. Every operation starts
from that array. Each stochastic item advances one continuous RNG sequence, so
different templates receive different random values while identical seeds and
path order reproduce the full result.

Example path:

```text
03.spin/scale-1.000/000001/02/001-incar/000-rotation/R2/INCAR
|       |           |      |  |         |            |  `- private INCAR
|       |           |      |  |         |            `---- second local variant
|       |           |      |  |         `----------------- first pert_spin item
|       |           |      |  `--------------------------- second INCAR template
|       |           |      `------------------------------ third AIMD frame
|       |           `------------------------------------- first perturbation
|       `------------------------------------------------- scale = 1.0
`--------------------------------------------------------- magnetic stage
```

### 6.3 Stage 4 files

| File | Type | Source or purpose |
| --- | --- | --- |
| `03.spin/POTCAR` | Regular file | Common POTCAR assembled in `potcars` order. |
| `03.spin/tasks.json` | JSON file | Stable ordered list of all submit-ready task paths. |
| Task `POSCAR` | Relative symlink | Matching snapshot under `02.disp`. |
| Task `POTCAR` | Relative symlink | `03.spin/POTCAR`. |
| Task `INCAR` | Private regular file | Generated from the matching template with this task's `MAGMOM/M_CONSTR`. |
| `OUTCAR` | Retrieved output | Main noncollinear VASP output. |
| `OSZICAR` | Retrieved output | Iteration and energy summary. |
| `CONTCAR` | Retrieved for relaxation submissions | Last ionic structure, which may be unconverged. |
| `fp.log` | Runtime log | DPDispatcher standard output/error log. |
| User forward files | Relative symlinks | Inputs from the selected `spin` or `fp` machine entry. |

The fixed file lists are:

```text
forward_files:
  POSCAR
  INCAR
  POTCAR
  + spin.user_forward_files, when spin exists
    or fp.user_forward_files otherwise

backward_files:
  OUTCAR
  OSZICAR
  CONTCAR, when the submission contains relaxation tasks
  + spin.user_backward_files, when spin exists
    or fp.user_backward_files otherwise
```

`tasks.json` drives `spin_action="run"`. The run phase reads exact paths from
this file rather than rediscovering directories or regenerating moments:

```json
{
  "tasks": [
    "scale-1.000/000000/00/000-incar/origin/000000",
    "scale-1.000/000000/00/000-incar/000-rotation/R1",
    "scale-1.000/000000/00/000-incar/001-canting/C1",
    "scale-1.000/000000/00/000-incar/002-scale/S1"
  ]
}
```

Manifest entries are local task directories, not group directories. Preserve
the original manifest rather than editing paths manually. Current baseline
entries include `origin/000000`. Run-only submission also accepts paths saved
by earlier layouts; it does not rename or move them.

## 8. Task-count relationships

Let:

- `Nscale` be the number of scale factors;
- `Npert` be `pert_numb`;
- `Nframe` be the number of frames in each AIMD task;
- `Nincar` be the number of initial magnetic templates;
- `Nspin` be the sum of local variants from all independent `pert_spin` items,
  excluding the baseline.

Then:

```text
POSCAR count in 00.scale_pert
    = Nscale * (Npert + 1)

AIMD task count in 01.md
    = Nscale * (Npert + 1)

snapshot count in 02.disp
    = Nscale * (Npert + 1) * Nframe

magnetic VASP task count in 03.spin
    = Nscale * (Npert + 1) * Nframe * Nincar * (Nspin + 1)
```

The final `+1` is the `origin/000000` baseline for every snapshot/template
pair. In the introductory example, `Nspin = 1 + 2 + 2 = 5`, not
`1 * 2 * 2`. With three frames, two templates, and two structural tasks:

```text
1 * 2 * 3 * 2 * (5 + 1) = 72 magnetic VASP tasks
```

If trajectories contain different frame counts, sum the frame-dependent terms
per AIMD task. The number of Stage 5 frames is determined by the returned
`data.extxyz`; one magnetic task is not assumed to contribute exactly one
frame.

## 9. Dependencies for stage-only runs

| Stage to run | Required input or existing directory | Directory created or used |
| --- | --- | --- |
| Stage 1 | Initial POSCAR | New `00.scale_pert`. |
| Stage 2 | Complete `00.scale_pert`, `md_incar`, POTCAR | New `01.md`; submit when MACHINE is supplied. |
| Stage 3 | OUTCAR and XDATCAR in every `01.md` task | New `02.disp`. |
| Stage 4 `make` | Complete `02.disp`, spin INCAR template(s), POTCAR | New `03.spin`. |
| Stage 4 `run` | Existing `03.spin` with a valid `tasks.json` | Submit existing tasks without rebuilding them. |
| Stage 4 `make_run` | Same input as `make` | Create and submit; create only when MACHINE is omitted. |
| Stage 5 | `tasks.json`, completed OUTCAR/OSZICAR for every task, and MACHINE `convert-data` | New `04.data/scale-*/out`; submit conversion, not VASP. |

Stages never silently overwrite an existing stage directory. Use
`spin_action="run"` for an existing `03.spin`. Run-only accepts legacy task
paths but does not change INCAR files, migrate directories, or perturb moments
again. Use a new `out_dir` to generate the current grouping layout. A
Stage-4-only output root must already contain the matching `02.disp` snapshots.

## 10. Checking outputs

### 10.1 Stage 1 structure count

```bash
find run_spin/00.scale_pert -name POSCAR -type f
```

Every scale should contain `pert_numb + 1` POSCARs.

### 10.2 AIMD outputs

```bash
find run_spin/01.md -name OUTCAR -type f
find run_spin/01.md -name XDATCAR -type f
```

Each count should equal the AIMD task count.

### 10.3 Real symbolic links

On Linux:

```bash
test -L run_spin/01.md/scale-1.000/000000/POSCAR
readlink run_spin/01.md/scale-1.000/000000/POSCAR

find run_spin/03.spin -name POSCAR -type l | head
find run_spin/03.spin -name POTCAR -type l | head
```

POSCAR and POTCAR must be actual symlinks, not copied files.

### 10.4 Snapshot count

```bash
find run_spin/02.disp -name POSCAR -type f | wc -l
```

### 10.5 Magnetic task manifest

```bash
python -m json.tool run_spin/03.spin/tasks.json
```

Every relative path must identify a real task directory containing at least
POSCAR, POTCAR, and INCAR. Completed calculations also contain OUTCAR and
OSZICAR.

### 10.6 Magnetic dataset export

```bash
python -m json.tool run_spin/04.data/selection.json
find run_spin/04.data -path '*/out/data.extxyz' -type f
find run_spin/04.data -path '*/out/set.000/spin.npy' -type f
```

`selection.json.selected` records every completed task and `rejected` is empty.
Within each scale, all arrays under `out/set.000` must share their first
dimension; `energy.npy` is one-dimensional.

## 11. Key interpretation notes

- Numeric prefixes in `00.scale_pert` through `04.data` describe processing
  order, not calculation indices.
- Stage 2 `000000` is the structurally unperturbed scaled configuration, not an
  AIMD frame.
- Stage 3 `00` is the first XDATCAR frame.
- Stage 4 `origin/000000` is the unchanged magnetic baseline.
- String `spin_incar` adds no INCAR index; list input always adds
  `###-incar`.
- Separate `pert_spin` items independently transform the initial moments. The
  indexed mode directory is a category; its local variants are VASP tasks.
- Parameter combinations remain inside an item. Rota_Cant is the explicit
  combination of Rotation followed by Canting.
- Stage 2 always retrieves OUTCAR and XDATCAR. Stage 4 always retrieves OUTCAR
  and OSZICAR; relaxation submissions additionally request CONTCAR.
- Preserve `03.spin/tasks.json` together with the task directories.
- Preserve the full stage relationship when moving output. Moving `01.md` or
  `03.spin` alone can break relative POSCAR/POTCAR links; external user-forward
  links also require their source files.
- Every generated Stage 4 INCAR writes identical three-component arrays to
  that task's `MAGMOM` and `M_CONSTR`.
- Stage 5 reads `tasks.json` and completed VASP outputs, retrieves extxyz
  through the MACHINE `convert-data` job, and writes `04.data`; it does not run
  VASP again.

## 12. Additional output for Stage 4 relaxation

Stage 4 keeps user `NSW`, `IBRION`, and `ISIF`. For example,
`NSW=50, IBRION=2, ISIF=3` enables structural and cell relaxation without
adding another stage. Each relaxation task contains an additional CONTCAR:

```text
03.spin/.../000-rotation/R1/
|- POSCAR -> matching 02.disp snapshot (initial structure)
|- POTCAR -> 03.spin/POTCAR
|- INCAR
|- OUTCAR
|- OSZICAR
`- CONTCAR   last ionic structure, potentially unconverged
```

When static and relaxation templates share a submission, the common backward
list requests CONTCAR for all tasks; only relaxation tasks require it for final
structure validation. A valid CONTCAR is nonempty, parseable by pymatgen
`Poscar`, and has the same atom count and species order as the input. Lattice
and coordinates may differ. It never replaces the POSCAR symlink or the
`02.disp` source snapshot.

Normal-termination checks allow multiple ionic steps and early stopping.
Structural convergence is assessed separately from VASP's convergence marker.
A normal exit without that marker produces a warning, and the task may still
be included in the normally terminated count. See
[Stage 4 structural and cell relaxation](doc/init/spin-init-usage-en.md#stage-4-structural-and-cell-relaxation).

## 13. `04.data`: magnetic data conversion

Stage 5 can run alone with `"stages": [5]` when MACHINE contains
`convert-data`. It requires every task in `03.spin/tasks.json` to have
terminated normally and exports all of them.

```text
03.spin/scale-1.000/data/
|- OUTCAR-1 -> completed magnetic task OUTCAR
`- OSZICAR-1 -> matching OSZICAR

04.data/
|- selection.json
`- scale-1.000/
   |- data -> 03.spin/scale-1.000/data
   `- out/
      |- data.extxyz
      |- type_map.raw, type.raw
      |- box.raw, coord.raw, energy.raw, force.raw
      |- force_mag.raw, spin.raw, virial.raw
      `- set.000/
         |- box.npy, coord.npy, energy.npy, force.npy
         `- force_mag.npy, spin.npy, virial.npy
```

`convert-data` runs against each scale's `data/` input. The terminal simple
command is `nequip-data`; Stage 5 creates remote `out/`, supplies
`-p data -o out/data.extxyz` when absent, and retrieves the resulting file.
`out2npy` writes raw rows and `set.000/*.npy` in the same local `out/`.

Every numeric raw file has one row per frame. `energy.npy` has shape
`(nframes,)`. The workflow computes `spin = spin_length * initial_magmoms`,
maps `force_mag` from `spin_forces_vert`, and obtains
`virial = -volume * stress` from the extxyz fields.

`selection.json` contains `selected` and `rejected`. Each selected record stores
the source task, scale, and per-scale index; `rejected` is empty. Missing or
incomplete tasks raise an explicit error. Existing `04.data` is never
overwritten.
